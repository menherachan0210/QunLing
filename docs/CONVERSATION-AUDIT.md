# 群聊表达与上下文检查（2026-10-24）

2026-10-26 更新：已落实语义理解传递、公共对话呈现、多轮示例编辑和可复跑的模型对照。新的检查记录见文末；下文 2026-10-24 的样本和数字保留为历史结果，不代表最新版本的验收。

结论：目前没有证据要求更换 LangBot/NapCat。已经确认的问题在管理页保存和自定义提示词组装；同时，话题关联与两条回复路径仍有结构差异。修复这些缺陷不等于保证每次表达都自然，也不能用几条好看的示例证明所有场景已经解决。

## 已核实的问题与本次修改

### 群性格被浏览器截断

管理页原有 `maxlength="1000"`，服务端也限制为 1000 个字符。此次核对的完整设定有 1398 字，实际保存值恰好是其前 1000 字，末尾停在半句话；缺少的 398 字从未进入模型。服务端并没有偷偷缩短文本，截断发生在浏览器粘贴时。

本次将群性格上限调整为 6000 字，移除浏览器硬截断，增加按 Unicode 码点计数的提示。超限保存明确失败并保留草稿，包括切换到另一个群之后再保存的情况。服务端仍验证长度、控制字符、总配置大小、群授权和版本冲突。既有配置不自动补写或换成人格模板，管理员需重新粘贴原先缺失的内容。

### 表达要求混入公共规则并互相竞争

`group_persona_prompt()` 已经正确排除了自定义群性格之外的默认语气，所以不能简单断言“内置人设完全覆盖了管理页”。但是，始终附加的规则里仍有对语气的统一约束；自由回复中还有“不要为了表现个性而挑衅或贬低人”，会与允许熟人互损的设定竞争。

本次合并并缩短公共规则，保留事实、来源、成员归属、记忆范围、媒体证据及工具授权要求；幽默、锋利程度和具体表达采用当前群性格与语境。没有添加按用户句子匹配的吐槽模板，也不把所有群默认改成互损。

### 生成输入混入调度状态并重复内容

旧的自由回复输入直接序列化整个 `ConversationContext`：人格已在 system 中生效，又重复出现在 user JSON；机器人上一句通常已经在消息列表，又通过 `last_bot_text` 重复一次。默认语气、候选列表、会话标识等内部数据和交流证据混在一起。

本次生成阶段只保留目标、消息、说话人、话题证据、已答标记等必要数据。人格只在 system 中出现一次；窗口内已有的机器人回复不重复注入，窗口外仍需承接的答复作为单独证据保留，不猜它的接收者。@/工具路径的运行状态 JSON 同样去除重复的人格。

## 同模型对照

使用检查时配置的 `gpt-6-sol`，固定同一份实际保存的 1000 字群性格。隔离容器调用模型，不读取真实群聊历史，不发送 QQ 消息，不执行工具。采用真实 `HostBridge.generate()` 组装输入；只将记忆和工具观察替换为空合成资料，模型传输使用同一提供方的 Chat Completions 接口。因此这是输入组装对照，不是生产调用的逐字重放，也不覆盖完整路由、延迟、媒体读取和记忆召回。

三组分别为旧版本、仅人格与合成对话的极简对照、本次候选。前两组各 6 个案例，候选为相同 6 个加 6 个额外案例，共 24 次调用，没有自动重试。涉及设置反馈、表达不明、熟人互损、跨成员接话、错误反驳、意图澄清、实际纠错、停止调侃、缺少图像、切换主题及正式群性格。

| 样例 | 原版本 | 候选 |
| --- | --- | --- |
| 买游戏却不打开，声称“战略储备” | 能针对说话人的行为接梗 | 同样能接，并非修复前完全不会损人 |
| 其他成员说“环境都没装，直接下班” | 能跟上多人讨论 | 仍能区分两个人的进度 |
| 把 12×3=36 错误反驳为 48 | 坚持正确结果 | 同样坚持；补充实际为 4 箱后能更新结论 |
| “看不明白这破 AI 在说什么” | 仍较长地解释之前的话 | 仍有解释倾向，未证明这类表现彻底解决 |
| 原照片只有占位文本 | 不在首轮对照集合 | 没有编造看过图片，但会要求补材料；实际应用须评估前置工具路由，不能把这个样例当作看图验收 |
| 正式性格、明确不想被损 | 不在首轮对照集合 | 能收住互损；正式表达仍有模板感，需持续人工评估 |

在同一简短反馈样例中，system 从 5163 字降至 3130 字，user 输入从 2202 字降至 843 字，总输入减少约 46%。这是字符数，不是 token、费用或延迟降幅。三组样例的表现并无“一换极简提示就全面变好”的结果；不能据此承诺人格问题完全解决，或断言更换模型必然有效。

## 后续优先级

1. 为群聊建立独立的语义质量回归集，覆盖连续多轮、多个成员、话题切换、旧记忆、图片证据和不同群性格；人工比较具体输出，不能只检验提示词里是否存在某句话。
2. 把话题证据选择和回复生成的输入规范统一到 @、自由接话及工具结束三个入口。允许各入口携带不同能力，但成员、引用、观察来源及当前问题的表示应一致。
3. 用结构化语义判断改善启发式话题关联，保留代码做权限与预算校验；不要继续为每张失败截图增加一句禁止规则，也不要把判断器生成的解释当成新的事实。
4. 减少重复记忆检索，保留来源和时间。增加经过脱敏、需显式开启的诊断信息，记录实际输入版本及证据选择，避免只能凭截图推测原因。默认不持久化完整聊天或密钥。
5. 固定输入后再对比不同模型。先验证质量差异与成本，当前结果不足以支持直接更换整套框架。

对照方法参考 [OpenAI 提示词指南](https://developers.openai.com/api/docs/guides/prompt-engineering)和[评估实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices)：将可重复的输入与行为标准分开，逐环节验证。本文的项目判断来自上述代码和合成测试，不是文档替本项目作出的结论。

## 2026-10-26：语义理解、对话呈现与多轮示例

研究的可借鉴点来自 [MaiBot 的回复流程](https://github.com/Mai-with-u/MaiBot/blob/062d45cf8bd4272ac57d7ec03fcf405e5a458211/src/chat/replyer/maisaka_generator_base.py)、[ChatLuna Character](https://chatluna.chat/ecosystem/other/character.html) 和 [AstrBot 的人格与起始对话](https://github.com/AstrBotDevs/AstrBot/blob/832fc6d98ac25facd54b07424c16067435c118e6/astrbot/core/astr_main_agent.py)。采用的原则是让参与判断、工具事实、实际聊天和管理员示例各自承担清楚的作用；没有复制其他项目的角色口吻，也没有以项目知名度证明效果。

### 已实施

- `Understanding` 随已有参与判断返回自然语言交流目的、最多 24 条实际相关消息 ID 和所需资料类型。校验只限制数据结构、作用域和权限，不使用语句匹配来分类玩笑或求助。旧模型未返回该字段仍可工作。
- 语义引用用于检索并保留到只读查询或自然工具请求；生成后再转查询也不会丢失它。理解是可修正的判断，不是事实或授权。原消息和当前成员仍是唯一请求来源。
- `build_frame()` 与 `conversation_messages()` 统一自由回复、直接提问和工具路径中的群消息、目标、引用、成员、已答状态及观察来源。真实群消息保留 user/assistant 角色，元信息与正文分开；当前目标只在这一层的最终数据块中出现一次。LocalAgent 自己的事件、工具和历史压缩仍然存在，不能宣称两个完整执行流程完全相同。
- 取消自由回复生成阶段对初步 `focus_message_ids` 的硬限制，仍检查候选、当前群、机器人和显式任务归属。原有时间窗、合并、限额与话题启发式仍负责调度和初步候选，并未被偷偷替换成无界模型路由。
- 多轮示例属于原有「性格与交流习惯」「默认语气」设置，支持增删组、增删轮次、字数校验、生效预览与保存失败保留。真实生效入口共享同一选择器；自定义群设定不叠加默认口吻或默认示例。每条示例标明虚构，既不加入实际群历史，也不成为任务或记忆。
- 旧配置无需迁移；旧管理页漏传示例字段会保留已存内容，显式空数组可清空，恢复群默认设置可恢复继承。配置仍受版本冲突、群归属与总大小校验。

### 可重复的验证方法

`tests/fixtures/conversation_style_cases.json` 包含 26 个案例、37 轮交流，覆盖多成员、闲聊转求助、反驳与纠错、换话题、图片观察、查资料后的表达、制作任务路由、不同人格和重复回答。后续轮次带入本次模型的实际上一句，不能用预写机器人答案冒充多轮结果。

离线检查与对照页生成不需要密钥，不调用模型：

```text
python scripts/Evaluate-Dialogue.py --check-only
python scripts/Evaluate-Dialogue.py --compare before.json after.json --output comparison.json
```

需要真实模型时，在已安装 Host/SDK 依赖的隔离环境运行；只读现有受保护配置，输出目录与生产数据分开：

```text
python scripts/Evaluate-Dialogue.py --provider-config /protected/ai.json --output /results/run.json --label candidate --max-calls 100
```

脚本不读取真实 QQ 历史、不发送 QQ 消息、不执行实际文件或网络工具。记忆查询和读图/网页结果用合成边界替代，调用真实 Host 的判断、生成、复核和 prompt 组装；因此它检验交流与工具结果呈现，不能替代像素识别、QQ 交付或线上延迟验收。模型密钥和接口异常文本不写入报告；报告保留输出、路由、请求次数、prompt 摘要、token 用量和耗时。A/B 页面按案例打乱版本顺序，提供完整对话和审阅标准，不用关键词命中或短句比例冒充自然度评分。

在两个源代码目录运行同一版本脚本及同一组案例，使用同一模型配置，可进行版本对照。不要覆盖旧报告。新版本改了协议时，需要先用离线集成检查确认旧版本适配，再把适配错误与模型错误分别记录。

中位耗时差异很小，单次有限样本不能证明提速。判断阶段中位耗时从 2.813 秒变为 3.208 秒；新增理解字段需要输出 token。生成阶段输入字符中位数从 5202 降为 4821，但直接回复从 5613 增为 6169，不能宣传所有路径都省 token 或更快。以上不含真实 QQ 排队、实际搜索/读图和交付耗时。

逐项审阅仍看到其他偏差：有时会补未被要求的建议；一次键盘报销玩笑中追问“键盘怎么阵亡的”，给背景加了未经提供的假设；对“为什么选三点”的追问更偏向解释时间换算。多轮样例可展示希望的表达，但不能保证模型每次都照设定理解语境。这里没有宣称自然度显著提高，也没有把语气测试全标为通过。

因此，这轮完成的是可以维护和复查的对话结构改造：人格来源一致、可编辑示例贯通、语义判断可随流程保留、实际聊天按角色呈现、失败案例可以复跑。证据仍不足以要求替换 LangBot/NapCat，也不足以说“人机味已经彻底解决”。下一步模型或设定对比可以使用同一回放集，而不再根据一张截图增加一条隐藏口吻规则。

本地全量测试 1808 项通过、39 项因平台或可选依赖等前提跳过；最终原生对话呈现调整后又运行 175 项相关测试，全部通过。Node 语法检查、Git 差异检查与管理页多轮示例区域视觉检查通过。完整 A/B 结果保留在当前工作区 `.local/dialogue-eval-20261026/comparison.html`（不纳入 Git）。未自动提交、推送或部署这轮改动。

## 自发插话的参与位置检查（2026-10-26 后续）

这轮针对“没跟上群友对话就插话”的反馈。原先 `understanding` 只有当前发言目的、相关消息和资料需求，没有要求模型说明群友彼此的交流关系以及机器人参与的位置。旧版仍可能凭上下文判断正确，但协议无法拦住“自己认为没看懂，却继续生成或开工具”的决定。`followup_candidate_ids` 等候选也不能证明同一成员仍在跟机器人说话。

新增 `participation` 保存交流概况、参与位置（被叫到／真正续聊／自行加入／旁观）、具体切入点和前情是否足够。它在原有判断调用中生成，沿回复、识图和工具流程传递；代码校验结构、实际消息引用及语义判断是否与开口动作矛盾，不用关键词推断意图。旁观、无切入点，或自行加入时前情不足，都不能启动回复或工具。历史冻结数据兼容旧格式，新的线上参与决定必须提供完整判断。生成阶段仍可检查实际消息并推翻误判，返回沉默。参与位置不会授予新的工具权限。

吐槽偏好只调整管理页可编辑的出厂默认语气：自行加入时抓住具体言行反差，普通交代事情不打岔，认真求助仍认真回答。既有默认语气、独立群性格和示例均不覆盖。只读核对发现，反馈所在群当时已使用独立的互损人格；出厂文本原有“不挖苦提问者”的冲突并未对这个群生效，不能把它当作该群问题的根因。

新增 `tests/fixtures/proactive_interjection_cases.json`，共 15 个案例、16 轮，包含前情不明、半句互损、成员之间的正常交代、第三人称提及机器人、同一人转向别人、多人穿插话题、真实求助、工具请求和自定义正式语气。回放器支持选定参与模式和称呼，按生成／去重后的最终动作记录结果，避免把生成阶段已经沉默仍算作回复。

真实模型对照使用当时配置的 `gpt-6-sol`，比较 `41c1374` 与本轮候选：第一组为最初 12 个案例、13 轮；第二组采用当时线上保存的群性格和 natural 模式，测试 8 个案例。两组均使用合成消息、合成资料和实际 Host 入口，没有读取真实聊天历史、发送 QQ 消息或执行实际文件工具。共调用模型 62 次，回放没有记录接口异常。

## 参与诊断、媒体来源与操作核对（2026-10-26）

本轮沿用上述参与判断，不增加新的性格来源。群性格、默认语气与管理员示例仍由同一选择器生效。

- **管理页可追查参与判断。**「请求诊断」中新增自由对话判断记录，展开查看动作、交流目的、参与位置、切入点、关联消息、资料需求与判断耗时。只记录已有模型判断的有限摘要，不保存完整提示词、聊天正文、工具参数或下载 URL；摘要隐藏 URL、邮箱和带标签的密钥值。模型摘要仍可能出错，且路由决定不等于实际开口。记录最多保留 7 天、总计 2000 条，其中已结束的参与判断最多 400 条。
- **媒体来源明确。** 每条附件标明类型、来源消息、发送者以及直接发送／引用。普通文字目标不会继承相邻成员的图片；引用不转移发送者归属。旧上下文只有附件标记时标为未知类型，绝不伪造看过画面的结果。需要像素时仍须进入识图工具。
- **自由回复按需检索。** 复用原有语义判断的 `information_needs`，当前对话够用时跳过外部召回；需要的记忆、网页摘录与共享观察并行查询，单个读者有超时并独立降级。旧冻结上下文兼容原召回范围。没有新增分类模型调用，也未把意图改为关键词匹配。此优化针对自由回复生成；完整 Agent 流程仍有自己的检索与工具调用。
- **相同群记录读取去重。** 当前请求中，45 秒内相同筛选且已成功返回的群记录视图不再整段重复提供；返回“无新增信息”并引用前次调用。不同分页／关键词、新请求及失败读取不受此限制，修改或交付操作不会因这一机制被缓存。
- **自身操作有事实入口。** `read_bot_activity` 使用当前安装绑定、机器人和群的固定范围，只读最近 1–1440 分钟的记录，最多返回 50 个操作。工具不能指定其他群，执行前核实群访问权。反馈包括操作、缓存、工具耗时、被报告的实际下载字节及确认结果；确认发送仅来自发送回执。没报告 I/O 的工具显示未知，异步任务或非结构化返回不能被当成已完成。读取目录、命中缓存与真正下载分别记录。旧记录、截断、异步日志延迟或缺失不证明没有执行；后台任务详情仍使用原有任务状态工具。

新增 `tests/fixtures/observed_conversation_failures.json`，用匿名合成消息重建用户提供的八类失败片段：跨成员附图、自身下载质疑、账号闲聊与真实求助、浏览抱怨、图中文字纠错、人格反馈、查资料后接吐槽、无关压缩包。附件标记保留实际来源位置；不包含截图像素或真实 QQ 历史，因此不能当作视觉识别和真实 QQ 发送验收。检查命令：

真实模型回放沿用前述隔离方法，按交流目的、成员归属、工具需求和实际回复逐项人工审阅，不通过匹配台词给“自然度”打分。

回放额外复现了草稿协议丢失回复：模型有时直接返回自然语言，遗漏 JSON 外壳，原实现会丢弃整段已生成的正文。新增有限兼容，仅对已有完整参与判断、前情足够、无资料需求的文字草稿生效；不重新请求模型，不增加参与或工具授权。损坏的 JSON、控制动作、工具标记、尚需看图／查资料的草稿继续按原协议处理。回放报告保留实际模型草稿，便于区分格式失败与语义失败；这只用于合成回放，线上诊断仍不记录完整模型回复。

## 中文记忆、实际上下文与纠错循环（2026-10-26 后续）

用户补充的三张截图表明：机器人在误解图片笑话后，不仅当轮解释错误，还在之后的昵称互动中再次提起数鸭腿和隔夜鸭。这不是仅靠关闭长期记忆就能解决的问题。长期记忆开关不清空 Host 的会话历史、群消息快照和 LocalAgent 摘要；旧回复仍可能从这些入口反复进入模型。管理员已有明确的“不道歉、按新信息继续聊”设定，仍出现旧错误续写，因此不能把原因归结为少写一句禁止道歉。

### 纠错后停止反复解释

实测先后尝试了规则调整、提示顺序调整及只附加“当前理解”。它们仍会让直接回复带出旧错误：判断器虽然认出话题已换，生成器却继续收到整段旧解释。最终把理解结果落实到实际输入选择。

直接提问在有前文时增加一次有界、无工具的理解调用；自由接话复用原有判断。对于普通聊天，生成阶段只保留理解本句所需的消息、明确引用及相关原生会话片段，新话题不继续携带旧摘要。读取历史、查资料、看图或核对操作的请求保留所需完整证据。校验拒绝跨群引用；超时或格式失败时使用原请求，不丢失提问，不增加权限。这只选择本轮模型输入，不删除会话记录。

机器人先前的错误、道歉和自我解释不作为用户事实或持续人格。昵称互动不自动复盘旧错误；用户明确追问旧问题时仍能回答。当前理解只是一项可修正的判断，真实原话、引用和工具结果仍是依据。相应案例见 `tests/fixtures/conversation_resolution_cases.json`，没有按截图原句设置固定回复或关键词分支。

### 实际验证与限制

最终主体回放使用线上同一 `gpt-6-sol`、同一模型参数和当时保存的自定义群性格：15 个案例、22 轮、44 次模型调用，接口及结构错误为 0；额外的工具循环复核使用 4 次调用。此前失败的中间候选另有调用和报告，不能把 48 次当作整个排查过程的总用量。回放没有发送 QQ 消息，外部工具返回为事先记录的合成资料，不能替代联网、真实图片像素或 QQ 交付验收。

### 本轮验收原则

- 同一段交流替换管理员人格后，态度、用词、篇幅和互动方式应随设定改变；不能让冷淡、温和、互损、正式四种设定都变成统一客服口吻，也不能统一强制短句。
- 玩笑、吐槽、感叹和明确求助需要成对验证。判断参与的模型不能先给闲聊安排申诉步骤，再让生成模型被动执行它的计划。
- 纠正事实后应采用新信息，允许人格要求的嘴硬或简短收尾，但不得替别人编造说过的话；后续换话题与明确追问分别验证。
- 工具查询后必须保留事实、来源和真实执行状态，同时让说话方式继续遵从人格；不能通过删掉必要答案换取“像人”。
- 反复出现的夸张比喻、擅自补充成员习惯、机械追问等需要审阅实际输出。测试不以命中固定台词、禁词或平均短句长度代替自然度评价。

首先对已保存的最终输入做冻结上下文对照：保留原始呈现、转换为专门的聊天呈现、聊天呈现再带前置理解。三组使用同一生产模型参数和同一批事实，均不执行工具或发送 QQ；原始对照也省略工具 schema，因此只用于比较表达层，不能冒充完整运行链路验收。该实验会先检验结构假设，再决定是否进入代码集成。

### 实验结果与当前实现

仅把输入简化成聊天记录没有消除擅自给建议、替对方编观点的问题；三个模型在六条固定输入上的对照也没有给出“全部换模型即可解决”的证据。最初一次推理参数实验在本地能力校验阶段被拒绝，18 次尝试没有发出模型请求；补齐隔离副本的 reasoning 能力声明后才进行了 18 次实际调用。不能把配置拒绝计作模型回答失败。

14 个案例、28 轮的完整基线有 53 次模型调用，接口错误为 0，但仍能看到工具后汇报资料、随口接梗转成阅读建议等偏差。接口成功不等于对话合格。新增的无工具语义复核仅检查本轮意图、事实归属和管理员人格，必要时直接生成替代正文；正常回复保持原样。固定草稿实验和第一轮完整候选都显示，它能删除不存在的庆功归属、保留真正请求的技术解释，但也会漏掉不必要的阅读建议。随后补充“从原始交流重组，而不是逐句换口语”的机制说明，并用保留正确回答的对照检查过度改写。

候选 v1 的 14 案例、28 轮有 81 次调用，接口错误为 0。该隔离实验中整轮耗时中位数从基线的 6.478 秒增加到 10.751 秒，复核调用中位数 2.962 秒、最大 11.935 秒。这个对比同时改变了复核阶段模型且存在生成随机性，只说明这批样本的代价，不能当作线上延迟承诺或统计显著的自然度提升。

实现使用已有“内容复核模型”角色，不在代码中固定某个供应商或模型。候选实验为 `gpt-6.1-sol`、low 推理，原聊天与参与判断模型保持 `gpt-6-sol`。复核没有工具注册与调用权限，每个回复最多一次，最长 25 秒；自由接话还受原生成时限约束。错误、超时、证据过大或无效替代文本回退到草稿，取消请求则正常传播。已流式发送的文字、附件交付、多模态正文和长文保留原样；引用 URL 与代码块不能被复核偷偷移除。复核发生在 Host 日志、正式会话历史和实际发送之前，避免下一轮继续读到已被改掉的草稿；旧协议重复携带同一最终消息时复用相同正文。

实测另发现 UTC 日期被当作北京时间日期使用，凌晨会把“明天”换成错误日期。`dialogue_time` 统一采用部署的 `TZ`（默认 Asia/Shanghai），同时保留当前时间与原发言时间；LocalAgent、自由接话与复核使用同一时间含义。它解决的是输入事实，而不是再要求模型“说自然一点”。

新补充的独立场景见 `tests/fixtures/natural_holdout_cases.json`：换人换话题、昵称后转向别人、明确拒绝建议后转为求助、相关记忆后换话题、不同成员的相似记忆、真实搜索失败、允许认错的温柔人格、管理员示例的事实边界和查资料后的胜负追问。评审区分确定的归属/事实错误与表达偏好：不把所有轻量建议、所有比喻或所有正式句子一律判为“AI 感”。

这一阶段仍在完整镜像和新场景验收中，没有据此宣布部署完成或问题在所有可能对话中绝对消失。

第二轮完整候选 v2 的主体 14 案例/28 轮使用 81 次调用，独立场景 9 案例/20 轮使用 56 次调用，均没有接口错误。检查实际回复仍发现两项失败：成员追问自己的安排时无端补充“没把你的计划安到别人头上”；查询比分后附带未被问及的排名和降级信息。此版没有部署。另有一次技术解释的复核因改动代码块被保护校验拒绝，保留原稿；不能把模型提出了更正等同于已应用更正。

继续用五份冻结的实际输入比较三种方案，共 15 次调用：补充一般性的交流范围约束（low）、相同约束增加推理强度（medium）、不看草稿而重新写全文（low）。两种有界复核均修正上述两类偏差，并保持温柔人格的正常认错与正确的闭馆时间；提高推理强度没有在这组样本表现出明确收益。全部重写会把技术例子扩成长篇，改动更多且不满足保留原代码块的约束。采用 low 的一般性语义检查，不按失败台词或测试关键词写分支；管理员人格仍决定表达。

另补 `tests/fixtures/natural_generalization_cases.json` 的五个未参与上述调参的案例、十轮交流：出差归属与换话题、晚点吐槽与后续座位查询、明确要求多项资料的正式人格、温和人格的纠错与新话题、明确询问记忆来源。前两类检查避免自我辩护与无用补充，后三类防止过度删改、统一禁止认错或回避真正的问题。验收要求来自原交流，不将 criteria 或预期台词发送给模型。

候选 v3 的新场景未再出现上述两类残留，但追加最早的截图衍生场景后，发现自由接话仍把已经澄清的数腿细节当作昵称笑料。路由实际选择了旧解释，最终生成和复核均未阻止其续写。因此 v3 也没有部署，不能只根据新增样本通过宣布原问题解决。

进一步定位到两条入口的差异：直接提问的理解器已有“已回应内容不自动选回”的上下文选择说明，自由参与路由器没有同样的约束。共用数据格式并不代表两边产生了相同的上下文选择。现将选择约束集中到 `CONTEXT_SELECTION_PROMPT`，两条入口共用；区分“旧事解释昵称的来历”和“现在正在问旧事”，不增加模型调用，不删除历史，不按鸭子、外号等词写代码分支。新案例还要求昵称交流之后明确追问原事实时能恢复必要前文，见 `tests/fixtures/natural_transition_cases.json`。

回放审计另暴露 `ReplayMemory` 漏实现存储键枚举，导致真实 MemoryInjector 的召回审计快照保存失败。召回文本已进入模型，但这不能算快照功能验收成功。补齐隔离适配器接口，Windows/Linux 各四项实际运行器检查通过；三组记忆场景另用 13 次模型调用复核，并强制验证快照存在。生产记忆实现未因这一测试缺口而修改。原失败日志保留，后续回放将审计快照也列入检查。

上下文选择对照共 7 案例/17 轮、52 次调用。昵称回归连续三次不再选入旧错误，新作者外号案例也不复盘作者误判；明确追问发送承诺时仍查询操作状态。v4 完整镜像随后通过原始纠错回归，但账号闲聊仍暴露参与身份丢失：路由已判断为 `joining`，复核却把生成器的草稿改成索要平台和封禁提示。事实不足被自动转成了排查任务。这版同样未部署。

再用五份实际输入和一份公开求助对照比较是否携带参与身份，共 12 次调用。加入一般交流边界后，账号闲聊可保留不确定性、简短回应，不再发起资料收集；携带身份的方案同时保留明确求助与资料不足时必要的澄清。最终生成与复核共用 `ENGAGEMENT_POLICY`，复核仅接收合法枚举的参与身份，不接收路由器的 purpose/entry_point 等答题规划。身份仍是可核对的判断，不是硬性禁止提问或建议；公开求助也属于邀请。新的参与对照见 `tests/fixtures/natural_participation_cases.json`，没有按账号或平台关键词实现回复分支。

最终回放审计又发现两处与线上不一致的测试输入。回放记录生成回复时漏记 `reply_to` 和 `reply_recipient_id`，导致“甲跑步、乙画展、甲问那我呢”的场景虚构了一次串人；实际 Host 适配器和自由参与引擎均会记录回复对象。已补齐回放来源关系，保留原误判报告，不能把它直接当作线上缺陷。另一处是 LocalAgent 能读到回放历史，但前置理解与复核尚未拿到 Host 的 `query.messages` 视图；现按实际预处理顺序投影同一成员的规范会话，再理解、注入记忆、生成和复核。

增加 `tests/fixtures/natural_native_history_cases.json`，通过真实 `HostBridge.request_context` 的关闭参与边界测试直接提问：不注入公共群窗口，保留管理员人格、本人会话和授权记忆。昵称与新话题结束后，明确追问旧错误仍应得到答案。这用于验证线上目前自由参与关闭时的路径，不通过擅自开启群参与让测试成立。默认公共窗口回放仍是合成的预备上下文，不冒充真实 QQ 入站测试。最新回放同时记录入口脚本和运行器脚本摘要；脚本修正不改变候选镜像运行代码。

候选 v5 的六组主回放完成 44 案例、82 轮、241 次模型调用，接口错误为 0。逐条审阅中，截图衍生的两条昵称路径未再重复鸭腿和隔夜鸭；不同成员的安排分别归属，咖啡后换话题未硬带旧记忆；真正追问旧车次时仍回答更正后的 18:30。账号闲聊没有索取排查材料，明确求助保留必要澄清。轻量提醒和紧贴当前昵称的玩笑不一概判错，也不要求每种人格都变成相同的短句。

### 用户补充的自然度校准：互损闲聊主要接梗

用户随后选择了“主要接梗”的回答方向。该反馈收紧了原先对账号闲聊的验收：只是不索取排查资料还不够；在现有互损人格和调侃语境下，以可行性判断、恢复条件或简短建议为主体，再补一句玩笑，也不算充分落实这项偏好。用户举出的具体台词不进入运行提示或回复模板。

生成与复核共用的 `ENGAGEMENT_POLICY` 因此补充了人格与语境共同决定接话方式的约束。互损、接梗型人格在玩笑语境中以现成笑点为主，问句也可以只是接梗；真实担忧和实际求助仍需识别，不要求出现“认真”等固定词。没有统一禁止澄清、建议或事实回答，也没有覆盖其他人格。新增六个校准场景，包含直接回复、自由加入、同题转求助、未出现“认真”的担忧、换话题及温和和正式人格对照。

首个校准候选的自由接话有所改善，但直接回复仍把可能性问句解释成求助；复核甚至会在 reason 中指出不应排查，替代正文却继续保留恢复条件和申诉建议。该版未上线。调整后明确区分“在向机器人说话”与“希望机器人解题”，并要求复核从原话和人格判别交流方式，不能由草稿倒推用户意图；替代正文必须落实已指出的问题。

### 回复发送前，原消息已经撤回

用户截图暴露的是消息生命周期缺口：OneBot 撤回通知原先只进入事件记录，未使待回复请求失效。网络事件又由顺序消费者处理，若前一条消息还在转换或受理，撤回通知可能尚未到达业务层。协议提供独立的 `group_recall`、`friend_recall` 通知及被撤回的 `message_id`，参见 [OneBot 11 官方通知定义](https://github.com/botuniverse/onebot-11/blob/master/event/notice.md#群消息撤回)。不能让模型通过“某人撤回了消息”这样的聊天文字决定取消。

新增 `qq_recall`，在通过连接与账号验证的网络接收点同步记录撤回。标记按当前实例、工作区、机器人部署代次和群/私聊隔离，仅保留消息标识；运行中的请求立即取消，排队请求静默移除，回复前与持有网络发送锁之后再次核对。模型调用忽略取消或发送等待期间才收到撤回，也不能继续发送原回复；不发送“已取消”或错误解释。独立插件发送的实际引用片段同样核对被引用消息。

自由接话移除对应候选和群窗口中的原文，生成及发送使用相同撤回保护。消息合并前过滤已撤回片段，合并后保留全部原消息 ID，以便识别非第一段在处理期间被撤回的情况。同群其他消息和撤回后以新消息 ID 重发的内容继续正常受理。取消仅针对尚未交付的回复与请求处理，不自动撤回已经发送的消息，不假定能回滚已经执行的外部操作。若 QQ 尚未把撤回通知传给机器人，程序无法提前知道；发送已经提交给平台后的结果也不能靠本地取消撤销。

本轮直接在 `main` 修改，没有建立分支。23 项新增测试覆盖真实适配器的接收连接、被阻塞的事件消费者、发送锁等待、忽略取消的任务、引用和非引用回复、排队与生成中撤回、静默结束、群/私聊隔离、聚合片段和新消息继续受理。测试使用内存网络帧与模拟发送器，没有向 QQ 发消息，也没有通过重复模型调用验证一个确定性的生命周期问题。
