# 启动、更新与恢复

全新部署按照[首页](../README.md)进行，Windows 从环境安装到排障的完整步骤见 [Windows 本机教程](WINDOWS.md)。服务器当前支持 Linux amd64，Windows 使用 Docker Desktop 的 Linux 容器。根目录 `bot.sh` 与 `scripts/Public-Bot.ps1` 操作同一份 Compose，Windows 的三个 `.cmd` 是后者的快捷入口。

## 设置入口

在服务器项目目录执行 `bash bot.sh url`，没有 Docker 权限时用 `sudo bash bot.sh url`，即可重新显示带 `#token=` 的完整设置链接，无需重启机器人。Windows 本机容器部署在项目根目录执行 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\scripts\Public-Bot.ps1" -Action url -OpenBrowser`，或直接双击 `Open-Bot.cmd`。

服务器部署默认只开放服务器自身的回环地址。自己的电脑需要保持 SSH 隧道连接；`ssh -N` 只转发端口，不会显示链接或令牌，输入密码后一直等待是正常的。基础设置只需转发 5310，完整的双终端操作步骤见[首页“服务器管理页：获取带令牌的链接”](../README.md#服务器管理页获取带令牌的链接)。需要高级管理页时，可使用以下隧道：

```bash
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:5310:127.0.0.1:5310 -L 127.0.0.1:5300:127.0.0.1:5300 -L 127.0.0.1:6099:127.0.0.1:6099 用户名@服务器IP
```

再开一个终端获取链接（项目位置不同时修改路径）：

```text
ssh -t 用户名@服务器IP "cd ~/QunLing && sudo bash bot.sh url"
```

在自己电脑的浏览器打开输出的**完整链接，包括 `#token=` 后的字符串**。若页面要求“设置令牌”，重新打开完整链接，或只复制 `#token=` 后的字符串填入并点击“连接”。令牌由部署自动生成，不是 AI API Key 或 SSH 密码。页面读取链接后会从地址栏移除令牌；新标签页或其他浏览器可能需要再次打开原专属链接。请私下保存链接，不要贴到公开截图、Issue 或日志中。

配置页可显示自动生成的 LangBot 管理账号。大多数用户只需使用配置页；需要修改提示词、触发规则和扩展工具时再进入管理后台。不要把管理端口直接暴露到公网。

重新保存 AI 配置会同步聊天、视觉、漫画、生图和搜索使用的模型或密钥；留空密钥保留已保存值。更换配置会重载相关插件，正在执行的漫画任务应先完成或取消，再修改配置。普通启动使用相同配置时不会反复重载。

设置页的“近期群聊范围”默认是 **24 小时、1000 条**，支持 1–168 小时、100–1000 条，聊天回看与改图参考历史共用这两项设置。修改后点击“保存并启用全部功能”；已保存的 API Key 不必重新输入。旧部署升级后自动采用默认范围，无需修改提示词或逐个配置插件。时间与条数是共同上限，QQ 可提供的历史和读取超时也会影响实际结果；扩大范围不会建立永久群聊档案。模型按需要继续翻页，读得越多可能使用越多输入额度。

## 在网页更新容器部署

在设置页打开“版本更新”，先检查版本，确认来源仓库与目标提交，再点击更新。默认来源是 `menherachan0210/QunLing` 的 `main` 分支；检查得到的完整提交 SHA 会固定为本次目标，执行时不会悄悄换成后来推送的提交。下载 ZIP 的环境也支持此流程，不要求宿主机安装 Git。

更新由独立 `updater` 服务发起，并由独立任务执行，因此更新器自身被替换不会终止这次任务。它准备目标源码并构建镜像，在替换运行服务前停止业务服务，对五个业务卷做一致性备份，校验备份 SHA-256 后才允许切换，再启动新版本并检查健康状态。页面可能短暂断开；恢复后重新打开原设置链接查看结果。插件安装以持久化包摘要为准，同一包恢复中时只等待，不重复安装。

备份放在独立 `update-data` 命名卷，该卷不备份自身。成功更新历史按下方保留策略自动清理，失败或未完成的记录保留。更新失败会恢复此次备份和旧镜像；若恢复过程也失败，则进入 `recovery_required`，禁止新更新并保留现场，不能把“发起恢复”理解为“恢复完成”。此时不要反复点击更新或删除卷，先保留现有卷与备份，再按页面阶段信息排查。自动恢复无法替代部署外的私有备份。

更新操作只管理 Docker 中的镜像和数据，不改电脑／服务器上的源码目录，不自动上传密钥或聊天。自定义分支、未提交改动及 ZIP 中的本地修改不会被合并到官方版本；维护自己的功能时应使用自己审阅的来源，或走下面的手动构建流程。版本检查只看已经发布到远端的提交，本机修改完成但尚未推送时不会作为可更新版本。原生 Windows/Python 部署没有网页一键升级支持。

`updater` 是唯一挂载 Docker socket 的服务。这个权限允许它管理宿主机容器和数据；app、wizard、NapCat 及插件不直接获得 socket。向导通过内部认证接口请求固定的版本检查和更新操作，不提供任意 shell 命令入口。只从你信任的仓库更新。

更新前请先完成或取消漫画等长任务，确认磁盘能容纳构建缓存和五个卷的备份。更新中不能 `down`；入口会阻止这类操作，也不要绕过入口手动停止任务容器。备份含 API Key、QQ 登录、聊天和记忆；不要上传 GitHub，不要随便删除 `update-data`。备份保留和磁盘清理应在确认当前版本正常且另有私有备份后处理，失败现场不自动清理。

需要人工恢复时，先排除磁盘、Docker 或下载故障，确认页面给出的任务 ID。页面无法打开、但 updater 仍运行时，可只读查看状态文件中的阶段与任务 ID（不输出凭据）：

```bash
docker compose -f deploy/compose/compose.yaml exec -T updater python -c "import json, os; from pathlib import Path; p=Path(os.environ.get('QQBOT_UPDATE_DIR', '/var/lib/qqbot-updater'))/'status.json'; d=json.loads(p.read_text()); print(json.dumps({k:d.get(k) for k in ('phase','job_id','message')}, ensure_ascii=False))"
```

然后从项目目录运行：

```bash
docker compose -f deploy/compose/compose.yaml run --rm --no-deps updater worker <job_id>
```

`<job_id>` 替换为该次失败任务的 ID，不要随意创建新任务。恢复命令继续处理已有任务及备份；执行完成后核对页面状态、实际镜像版本、QQ 连接和记忆数据，仍为 `recovery_required` 时保留现场进一步排查。

## 更新历史与磁盘清理

更新器在空闲时定期整理当前 Compose 项目的更新历史，默认保留最近 **2 次已成功完成的更新备份**，以及当前状态仍引用的任务。超出的成功任务通过目录、项目归属和备份完整性检查后，删除其备份、下载源码和任务日志。保留下来的任务所需的旧／新镜像、备份恢复辅助镜像、当前部署和所有现存容器引用的镜像均受保护；只删除本项目可确认无引用的历史镜像，不使用全局镜像或数据卷清理。

手工维护成功后也可以纳入自动清理，但必须先用 `deploy.updater.retention.register_completed_maintenance` 登记：在持有更新数据卷 `worker.lock`、没有更新进行时，提供任务目录、项目名、更新卷名、带时区的完成时间和维护日志文件名。登记会核对完成状态、实际部署快照、卷归属和备份校验和，生成 `maintenance.json`；不能通过改文件名或补一个“已完成”标记跳过验证。维护脚本应在成功收尾时登记，历史任务只能由运维人员核验后补登记。

仅备份 `langbot-data` 与 `setup-state` 的维护记录，和包含 QQ 登录数据的五卷完整更新记录**分别保留最近 2 份**，避免部分备份挤掉完整恢复点。已登记维护镜像按精确镜像 ID 确认归属；当前部署、保留备份及其他容器引用的镜像仍受保护。清理与更新、维护共用进程间锁，维护刚完成后会重新检查，不必等待下一小时。

失败、回滚、未完成、缺少元数据或尚未登记的手工维护任务不会自动删除，异常现场可能让实际保留数量超过 2 份；先查清原因再整理。清理失败只记录结果，不回滚已经成功的更新。它不会停止机器人或清空业务数据。

需要调整保留数时，在启动前设置 `QQBOT_UPDATE_KEEP_BACKUPS`（1–10，默认 2），通过本地 `rebuild` 应用到更新器；后续网页更新会延续该设置。Windows 和 Linux 容器采用相同策略。更新数据卷中的 `cleanup.json` 保存最近一次清理摘要，备份仍应另存到部署之外的私有位置。

**构建缓存与镜像是不同的空间占用。** 自动历史清理不会清空共享 Docker 构建缓存，以免影响同机其他项目的构建。需要释放缓存时，先确认所有项目都没有构建或更新任务，再执行以下命令；只清理可再生成的缓存，下次构建会重新下载／编译依赖：

```bash
docker system df
docker builder prune --all
```

按 Docker 提示确认后再用 `docker system df` 和磁盘统计核对实际释放空间；镜像和缓存可能共享层，不能简单相加。不要用 `docker system prune --volumes` 或 `docker compose down -v` 代替清理。

## 手动构建与源码开发

普通 `bash bot.sh up` / `Start-Bot.cmd` 会优先恢复已经启用的部署快照；不存在快照时才做首次构建，因此从旧下载目录启动不会自动降级。要应用本地改动，先完成私有备份，再在该目录运行 `bash bot.sh rebuild`；Windows 使用 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\scripts\Public-Bot.ps1" -Action rebuild`。此操作明确按本地源码构建，若本地目录仍是旧代码就会引入旧版本，操作前确认所用版本。

初次构建和安装插件都需要联网。缺少依赖或插件初始化失败时，向导不会假装完成；查看 `bash bot.sh logs`，恢复网络后重新启动服务。不要在新版源码上直接复用宿主机虚拟环境。

## 文件任务与存储

文件解析器、7-Zip、共享文件包和后台任务进程随部署安装，不需要另开服务或手工填写路径。容器的 `QUNLING_DATA_DIR` 已指向现有 `langbot-data` 卷中的 `qunling/`，文件、产物、任务和发送回执会随该卷一起备份。QQTextReader 保留原插件身份，重新构建后由初始化流程安装更新版本。

app 内的启动管理器同时托管 LangBot 与 `python -m qunling.daemon`；不应再手动启动第二份 worker。daemon 默认同时处理 2 个任务，解析另使用有内存、CPU、时间和输出限制的子进程。它只负责处理文件；明确要求生成后发来的最终附件可登记持久交付，由 Host 完成后向原会话发送，中间产物不自动发送。需要查询或取消时，可以向机器人明确提出并提供它此前返回的任务编号。

| 默认限额 | 数值 |
| --- | --- |
| 文件缓存 | 2048 项、512 MiB，单输入最多 40 MiB，保留 7 天 |
| 文件任务及参数／结果存储 | 1024 项、128 MiB；已结束任务保留 7 天 |
| 活动文件任务 | 每个工作空间／机器人／会话／发送者范围 4 个，全局 32 个 |
| 单个本地任务 | 总期限 10 分钟，最多 2 次执行机会；仅安全操作可自动重试 |
| 单个解析进程 | 约 768 MiB 内存、45 秒 CPU、65 秒墙钟时间 |
| 生成文件与发送附件 | 单文件 20 MiB，共享发送每轮最多 5 个；旧网页直发入口另限 2 个 |

结束任务由 daemon 启动时及运行期间定期清理；正在执行的任务不会因结束任务的保留期清理而丢失参数。过期资产先变为不可读取，在后续文件写入／删除时回收；闲置部署不保证到期立即物理删除。达到配额时新请求会明确失败，先保存需要的结果、排查异常堆积，不要直接删除正在使用的数据库。文件缓存不是长期归档，用户需要自行下载重要产物。

普通文件任务可在重启后按原期限和重试预算恢复；漫画和图片等付费任务保留原恢复规则，重启不自动重新计费。文件生成完成、QQ 已确认发送和发送结果未知是不同状态，未知结果不会自动重发。更新或更改模型配置前仍应先完成／取消长任务，不能依赖恢复机制跳过维护窗口安排。

## 备份与恢复

业务数据位于 `qq-ai-bot` Compose 项目的五个命名卷。必须把 `langbot-data`、`setup-state`、`napcat-qq`、`napcat-config`、`napcat-plugins` 一起备份，尤其不能丢失 `setup-state` 后把旧 LangBot 数据当作全新环境初始化。第六个 `update-data` 卷保存更新工作状态和自动备份，也应作为私有资料管理；它不是新的业务数据库。

1. 使用 `bash bot.sh down` 停止服务；不带 `-v`，数据保留。
2. 按 [Docker 官方卷备份方法](https://docs.docker.com/engine/storage/volumes/#back-up-restore-or-migrate-data-volumes)备份五个卷；可用 `docker volume ls --filter label=com.docker.compose.project=qq-ai-bot` 查看实际名称。
3. 备份是私有资料，含 API Key、QQ 登录状态、会话与记忆；加密保存，不上传 GitHub。
4. 恢复到同版本源码和空卷，保留卷名与 Compose 项目名，再运行启动命令。QQ 可能要求重新确认登录。

本项目暂不提供“一键清空数据”。不要把 `down -v`、删除卷或删除数据库用作排障步骤。

## 已有本机环境

原本已经安装 `langbot/.venv` 和 `napcat/` 的目录继续使用 `Start-Bot.cmd` 等旧入口；它不会自动迁移或重置当前机器人。维护脚本已集中到 `scripts/`，但所有原生数据路径保持不变。例如在项目根目录用 `langbot/.venv/Scripts/python.exe scripts/Configure-ChatStyle.py` 应用风格；Linux 的目标解释器是 `langbot/.venv/bin/python`。脚本清单见 [scripts/README](../scripts/README.md)。

原生 LangBot 启动脚本会自动检查并补齐 `qunling/requirements.txt` 的固定解析依赖、登记共享包路径并托管文件 daemon；首次补齐依赖需要联网。默认文件数据在 `langbot/data/qunling`，Windows 与 Linux 使用相同接口，无需为每个插件重复安装一套解析器。依赖安装失败时应先修复网络再重试，不要绕过启动检查运行缺少依赖的任务。

公开容器部署使用独立数据卷，不自动导入当前电脑的密钥或聊天。迁移时先停止旧服务，避免占用同一端口或同一个 QQ 同时登录；按照上面的备份策略迁移数据。跨系统不复制虚拟环境，QQ 登录状态也可能需要重新建立。原生环境到容器的数据转换尚未作为自动迁移路径验收，请先保留完整备份。

## 排障

| 现象 | 检查 |
| --- | --- |
| 构建下载失败 | GitHub、PyPI、Docker Hub 和模型下载站点是否可达；保留摘要校验 |
| 提示端口占用 | 是否还有旧版 LangBot/NapCat，或另一套部署 |
| `ssh -N` 输入密码后没有输出 | 没有报错时通常表示隧道已建立；保持窗口打开，在另一个终端获取专属链接 |
| SSH 提示 `Address already in use` | 本地转发端口已被占用；若已有指向同一服务器的隧道，直接复用 |
| 页面要求“设置令牌” | 用 `sudo bash bot.sh url` 获取完整链接，保留 `#token=` 部分打开；也可单独填写令牌后点击“连接” |
| 一直安装插件 | 查看 app、wizard 日志；首次依赖安装较慢，失败后恢复网络再重启 |
| 二维码未出现或过期 | 确认 napcat 容器运行；在设置页刷新，手机确认新设备登录 |
| 已登录但未连接 | 配置是否已保存，LangBot 与 NapCat 是否健康；查看向导状态 |
| QQ 已连通但 AI 报错 | 检查地址、Key、模型名和服务端接口；保存配置没有验证额度或模型能力 |
| 能聊天不能改图／搜索 | 服务是否真的提供 Images edits / Responses web_search，模型是否可用 |
| 文件任务长时间排队 | 先询问任务状态；检查 app 中的 daemon 是否启动、活动任务配额及磁盘空间；不要另外启动多份 worker |
| 文件提示不能读取或需要 OCR | 核对真实格式与[功能范围](FEATURES.md#通用文件流程)；扫描 PDF、旧 Office 文件和复杂嵌入内容不保证可解析 |
| 文件提示资源或存储超限 | 缩小文档、分批读取或导出；缓存受配额和 7 天保留期限制，不要直接清空数据库 |
| 新版本提示缺少解析依赖 | 确认已重新构建新版镜像或通过原生启动入口补齐；仅复制插件源码不会更新 Host 的处理进程 |
| 文件已生成但没有收到附件 | 查询任务与发送状态；发送结果未知时先检查 QQ，避免重复发送 |
| 更新后记忆似乎消失 | 先核对 Compose 项目名与卷名，不要重新建空知识库 |

提交 Issue 时提供系统、部署方式、版本、复现步骤和脱敏错误。不要发送设置链接、API Key、`secrets.json`、数据库、QQ 配置卷或完整群聊日志。
